# AI 실습 설명서: 아빠 어디가~ 자동 큐레이션

## 1. 과제 정의

이 과제는 AI에게 “여행지를 추천해 줘”라고 한 번 질문하는 작업이 아니다. 조사 기준, 데이터 계약, 편집 규칙, 품질 평가, 배포 조건을 스킬과 코드로 고정하고 매일 같은 절차를 재현하는 에이전트 자동화 실습이다.

핵심 질문은 다음과 같다.

- AI가 최신 공개 자료를 어떤 기준으로 선택하는가?
- 인기라는 표현을 어떤 수치로 제한하는가?
- 광고, 종료된 행사, 안전정보를 어떻게 보존하는가?
- 조사 실패가 사용자 화면을 망가뜨리지 않게 어떻게 막는가?
- 사람이 만든 규칙을 매일 같은 방식으로 실행할 수 있는가?

## 2. 구성 요소별 책임

### `AGENTS.md`

프로젝트 전체에 적용되는 조사·작성·팩트체크·독자·전문가·디자인 관점을 정의한다. 8개 역할 중 하나라도 9.5점 미만이면 게시하지 않는다.

### 루트 `SKILL.md`

이 프로젝트에서 AI가 따라야 하는 구체적인 표준작업절차이자 저장소의 정본이다. 출처 구성, 후보 수, 기간, 데이터 필드, 반응점수 계산, 카드 문구, 이미지, 접근성, 검증과 GitHub 게시 방법을 포함한다. `family-trip-mosaic/SKILL.md`는 기존 호출 경로를 유지하면서 루트 정본을 안내한다.

### Codex 예약 작업

스킬을 매일 18:00 KST에 실행하는 시계 역할이다. 스킬이 “어떻게 할지”를 정의하고 예약 작업이 “언제 할지”를 정의한다.

현재 자동화 설정:

```text
이름: 매일 아빠 어디가 갱신·배포
상태: ACTIVE
반복: FREQ=DAILY;BYHOUR=18;BYMINUTE=0
시간대: Asia/Seoul
```

예약 작업은 로컬 저장소를 사용하므로 컴퓨터와 Codex 데스크톱 앱이 켜져 있어야 한다. 실행 결과와 실패 보고는 Codex의 Scheduled 화면에서 확인한다.

### GitHub Actions

Codex가 `origin/main`에 push하면 `.github/workflows/deploy-pages.yml`이 다음을 수행한다.

1. 저장소 checkout
2. `node scripts/build.mjs`
3. `node scripts/validate.mjs`
4. 생성된 `index.html`이 커밋본과 같은지 확인
5. GitHub Pages 아티팩트 업로드 및 배포

GitHub Actions는 인스타그램을 조사하지 않는다. 이미 커밋된 결과를 검증하고 공개하는 CI/CD 단계다.

## 3. 매일 실행 프롬프트의 계약

예약 작업은 매회 다음 절차를 따른다.

1. `origin/main`, 현재 브랜치와 작업 트리를 확인한다.
2. 사용자가 아직 커밋하지 않은 변경을 덮어쓰지 않는다.
3. 공식 관광 계정 3개 이상과 고유 개인 계정 12개 이상을 조사한다.
4. 최근 30일 전국 후보 90개 이상, 서울·근교 후보 90개 이상을 만든다.
5. 로그인 없이 원문 접근이 가능한지 확인한다.
6. 게시일·확인시각·좋아요·댓글·광고·협찬·종료·예약·안전을 기록한다.
7. `좋아요 + 댓글 × 5`로 비교 가능한 공개 반응점수를 계산한다.
8. 전국 30선과 서울·근교 30선을 독립 선정한다.
9. 두 줄 이내 제목, 요약, 주의사항과 로컬 이미지를 갱신한다.
10. 빌드·데이터 검증·반응형 화면·접근성을 확인한다.
11. 8개 역할이 각각 9.5점 이상일 때만 커밋하고 push한다.
12. Pages 배포 결과를 직접 확인한다.

기준을 충족하지 못하면 수치나 점수를 만들어 내지 않고 기존 사이트를 유지한다.

## 4. 데이터 흐름

```text
공개 원문과 공식 운영정보
        ↓
후보 기록과 제외 사유
        ↓
반응점수·지역·계정 다양성 적용
        ↓
trips.json + assets/*.jpg
        ↓
scripts/build.mjs
        ↓
정적 카드가 포함된 index.html
        ↓
scripts/validate.mjs
        ↓
Git commit / push
        ↓
GitHub Actions / Pages
        ↓
방문 시 app.js가 최신 trips.json 재확인
```

정적 HTML과 런타임 JSON을 함께 두는 이유는 점진적 향상이다. JavaScript와 네트워크가 정상일 때는 최신 JSON을 반영하고, 실패하면 마지막으로 검증된 정적 카드를 보여준다.

## 5. GitHub에서 실행하는 방법

### 가장 쉬운 방법

<https://dahanpark.github.io/newscard/>를 연다. 이 주소가 실제 실행 사이트다.

### 저장소 파일 화면과 Pages의 차이

- `github.com/dahanpark/newscard/blob/main/index.html`: HTML 소스 코드를 보는 화면
- `dahanpark.github.io/newscard/`: 브라우저가 HTML·CSS·JavaScript를 실행하는 화면

GitHub 저장소에서 `index.html`을 클릭하는 것만으로는 실행되지 않는다. Pages가 정적 파일을 웹 서버로 제공해야 한다.

### Pages가 꺼진 저장소에서 설정

1. GitHub 저장소의 `Settings`로 이동한다.
2. 왼쪽 메뉴에서 `Pages`를 선택한다.
3. `Build and deployment`의 `Source`를 `GitHub Actions`로 선택한다.
4. `main` 브랜치에 워크플로와 사이트 파일을 push한다.
5. `Actions`에서 배포 성공을 확인한다.
6. Pages가 제공하는 공개 URL을 연다.

## 6. 검증 실습

### 데이터와 빌드

```powershell
node --check app.js
node scripts/build.mjs
node scripts/validate.mjs
git diff --check
```

### 화면

- 데스크톱: 카드 크기 위계와 12열 모자이크
- 태블릿: 제목·메타데이터 겹침과 필터 줄바꿈
- 모바일: 1–2열 재배치, 주의사항, 갱신 버튼
- 키보드: 필터와 카드 포커스
- 네트워크 성공: `최신 자료 불러옴`
- 네트워크 실패: `검증된 정적본 표시 중`

### 배포

- GitHub Actions 성공
- Pages HTTP 접근 성공
- 카드 수와 첫·마지막 카드 확인
- 원문 링크가 새 탭으로 열리는지 확인
- `trips.json` 확인시각과 화면 표시 비교

## 7. 평가 시 설명할 핵심

1. **스킬과 예약 작업을 분리했다.** 스킬은 재사용 가능한 방법이고 예약 작업은 실행 시각이다.
2. **AI 결과를 바로 게시하지 않는다.** 구조화된 데이터와 코드 검증, 8개 역할 심사를 통과해야 한다.
3. **실패를 안전하게 처리한다.** 새 조사가 실패하면 마지막 정상 배포가 유지된다.
4. **정적 사이트의 한계를 공개한다.** 페이지 방문은 새 조사를 만들지 않고 GitHub에 게시된 최신 결과만 가져온다.
5. **출처와 불확실성을 보존한다.** 광고·행사 종료·안전·예약 정보를 카드에서 숨기지 않는다.

## 8. 남은 확장 과제

현재 배포 데이터는 기존 단일 30선이다. `SKILL.md`가 정의한 최종 구조로 가려면 `nationalItems` 30개와 `seoulMetroItems` 30개를 분리하고, 빌더·검증기·필터를 60개 구조로 이전해야 한다. 이 이전도 후보 수와 출처 기준을 실제로 충족한 조사 결과가 있을 때만 게시해야 한다.
